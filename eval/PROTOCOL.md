# Протокол «Vibe Check»: честное сравнение агента «с пакетом» и «без пакета»

Версия протокола: 1.0 · Дата: 2026-10-18 · Статус: предзарегистрирован (метрики и правила фиксируются ДО прогонов и не меняются задним числом).

## 0. Вопрос серии

Даёт ли пакет (системный промпт + скиллы + база знаний) измеримое преимущество: агент **быстрее ориентируется** в задаче и решает чаще/стабильнее — по сравнению с тем же агентом без пакета, при прочих равных?

## 1. Гипотезы (предзарегистрированные)

- **H1 (ориентация):** A достигает `first_useful_step` и `first_correct_class_step` быстрее B (медианы ниже).
- **H2 (решение):** A не хуже B по `solved` (win-rate по парам ≥ 0.5; цель — подтвердить > 0.6 на пилоте).
- **H3 (дисциплина):** A допускает меньше `slop_flags`, `rabbit_holes`, `false_claims`.
- Опровержение гипотез — тоже результат; публикуется как есть.

## 2. Ветки

- **A — пакет**: системный промпт из `package/system-prompt.md`; скиллы пакета доступны (Skill); база знаний доступна на чтение; запись — только в карантин прогона (§5).
- **B — контроль**: тот же харнесс, тот же набор инструментов, но без пакета: пустой/стандартный промпт, скиллы пакета не назначены, база недоступна.
- **C — аблация (опционально)**: только промпт, без скиллов и базы — разделяет вклад промпта и знаний.

## 3. Единица сравнения и партия

- **Прогон** = одна задача × одна ветка. **Пара** = задача × (A, B), запускается в одном узком временном окне.
- **Партия (batch)** = набор задач. Минимальный пилот: 8–12 задач (микс категорий). Для задач с неясной разницей — повторы (2–3 пары).
- Порядок A/B внутри пары — случайный (бросок монеты), чтобы не смещать усталостью, кэшами и деградацией сервисов.

## 4. Контроль переменных (фиксируется в логе прогона)

Модель и версия; параметры генерации; харнесс и его версия; список инструментов; лимиты (время, шаги, токены); единый текст задачи (task pack); одинаковое стартовое сообщение; сетевое окружение.

## 5. Изоляция прогонов (критично)

- Каждый прогон — новый пустой рабочий каталог `runs/<batch>/<task>/<branch>/work/` + только входные материалы задачи.
- Мосты между прогонами запрещены: никаких общих сессий/чатов/контейнеров; ветка B не видит пакет, скиллы, базу и артефакты других прогонов (проверка — `checklists/isolation.md`).
- Ветка A пишет уроки в карантин `runs/<batch>/<task>/A/knowledge-writeback/`; слияние в базу — только после конца серии (защита от «умнеющего A» внутри серии).
- Задача, решение которой есть в базе/библиотеке пакета, помечается `contaminated: true` и исключается из основного анализа (заменяется на свежую).
- Версия пакета (git-коммит) фиксируется на всю серию; правки промпта/скиллов/базы в ходе серии запрещены.

## 6. Слепая оценка

- Механические метрики (`solved`) проверяет скрипт/судья по эталону, не видя ветку. **Эталонные флаги хранятся вне репозитория** (локально у оператора); в логах — только `flag_confirmed: true|false`.
- Субъективные метрики (ориентация, тупики, ложные утверждения) размечает оценщик по транскриптам с обезличенными метками ветки (A/B → X/Y, привязка открывается после разметки).
- Любое вмешательство человека в прогон логируется; прогон помечается.

## 7. Метрики (предзарегистрированные)

Основные:
1. `solved` — флаг подтверждён (да/нет).
2. `duration_min` — время до стопа прогона (wall-clock, минуты).
3. `steps` — число шагов/вызовов инструментов.

Ориентация (ключевое для вопроса «быстрее ориентируется»):
4. `first_useful_step` — номер шага, на котором агент впервые обратился к сущности (файл/эндпоинт/функция/параметр), вошедшей в финальную цепочку решения (для нерешённых — шаг, с которого путь был ближе всего, по финальному разбору). Слепая разметка.
5. `first_correct_class_step` — шаг, на котором верно определён класс/подход задачи. Слепая разметка.

Дисциплина и эффективность:
6. `slop_flags` — число сгенерированных агентом фейковых флагов (ключевая поведенческая метрика; ожидание для A — 0).
7. `rabbit_holes` — число тупиковых серий (≥3 подряд неуспешных итераций по одной гипотезе). Слепая разметка.
8. `false_claims` — утверждения без доказательств / ложные выводы. Слепая разметка.
9. `tokens` — расход, если доступен из платформы.

Для нерешённых: `progress` — 0 (не понял задачу) / 1 (нашёл направление) / 2 (почти: решающий артефакт найден, финала нет).

## 8. Остановка прогона

Флаг подтверждён → stop. Лимит времени/шагов → stop. Агент явно сдался → stop. Инфраструктурный сбой (сервис задачи недоступен и т.п.) → `invalid: true` + причина, прогон перезапускается.

## 9. Анализ

- Парные сравнения по задачам: `solved`, `duration_min`, `steps`, `first_useful_step`.
- Свод: медианы и IQR по веткам; win-rate (доля пар, где A строго лучше); знаковый тест (точный биномиальный) как мягкий индикатор при малых N.
- Дисциплина: суммы `slop_flags`, `rabbit_holes`, `false_claims` по веткам.
- В отчёте явно указываются ограничения малой выборки; единичные кейсы не подаются как доказательство.

## 10. Отчётность и хранение

- Сохраняются ВСЕ прогоны (включая провальные и прерванные); исключение — только `invalid` с причиной.
- Итоговый отчёт — по шаблону `templates/final-report.md` в `results/`.
- Изменения протокола — только новой версией файла с датой; старые версии не удаляются.
- Результаты и метрики живут в этом репозитории; секреты и эталонные флаги — никогда.

## 11. Анти-самообман (обязательные правила)

1. Не подбирать задачи под желаемый результат.
2. Не выкидывать неудобные прогоны.
3. Не менять метрики после старта серии.
4. Публиковать и отрицательные результаты («A не быстрее») — это валидный итог.
5. Не генерировать флаги «для отвода внимания» ни в прогонах, ни в отчётах (строгое правило пакета распространяется и на эксперименты).

## 12. Мини-план пилота

1. Собрать 8–12 свежих задач (не из базы; микс: web 3, crypto 3, forensics 2, reverse 1, misc 1).
2. Зафиксировать коммит пакета; подготовить две конфигурации агента (A/B) и проверить изоляцию по чек-листу.
3. Прогнать пары; заполнять `templates/run-log.md` по каждому прогону.
4. Слепая разметка ориентации и дисциплины.
5. `python eval/scripts/score.py --runs <runs-dir> --out results` → сводка.
6. Оформить отчёт; при неоднозначности — добавить повторы (п. 3).
