# CONTRIBUTING — правила контрибуции

## Что это за проект

`Professional-Vibe-Checker` — общий модуль для LLM-агентов CTF/Red Team: системный промпт, скиллы и накапливаемая база знаний, которые делают подключённого агента быстрее и надёжнее. Подключение — за 4 шага (см. [README.md](README.md)); внешние инструменты не требуются.

Принцип: **модуль должен ускорять, а не тормозить.** Поэтому вход для модели — один короткий файл ([AGENT.md](AGENT.md)), чтение — точечное, а записи в базу — только важные.

## Карта репозитория

```
AGENT.md        вход для модели (модульный режим)
CONTRIBUTING.md этот файл — правила для людей
package/        сам модуль: промпт, скиллы, база знаний, library, VERSION, CHANGELOG
tools/          обслуживание: sync_package.ps1 (установка скиллов), make_bundle.ps1 (сборка релиза), check_package.ps1 (гигиена)
.github/        CI: автопроверка гигиены пакета на каждый push/PR
```

## Как подключить модуль (3 способа)

1. **Репозиторий рядом с агентом** (clone/submodule). В системный промпт добавь одну строку: «Подключён модуль опыта: начни с AGENT.md в корне репозитория». Всё.
2. **Zip**: `tools/make_bundle.ps1` → `dist/redteam-pack-<версия>.zip` + `SHA256SUMS.txt`; распаковать рядом с агентом, вход — `package/START-HERE.md`.
3. **Платформа с файловыми скиллами** (например, Artex): `tools/sync_package.ps1 -SkillsTarget <каталог скиллов платформы>` (флаг `-IncludeLibrary` добавит категорийную библиотеку); содержимое `package/system-prompt.md` — в промпт агента. Имена каталогов скиллов не менять.

## Что можно добавлять и в каком формате

1. **Знания (главное).** Lesson-записи в `package/lessons/YYYY-MM-DD-<slug>.md` по шаблону `package/skills/hermes-knowledge-loop/SKILL.md` §3 + строка в `package/index.md`. Не уверен в важности — положи в `package/lessons/_inbox/`, мейнтейнер решит.
2. **Тактики/чек-листы.** `package/tactics/<тема>.md`; обновляй существующие файлы, не создавай дубли.
3. **Скрипты.** `package/toolbox/<name>.<ext>`: самодостаточные, кроссплатформенные (или два варианта Win/*nix), с заголовком-комментарием «назначение / использование / проверено на».
4. **Скиллы.** `package/skills/<name>/SKILL.md` в формате agentskills.io (frontmatter `name` + `description`, затем суть без воды). Имя каталога = имя скилла, уникальное; существующие не переименовывать.
5. **Library-скиллы (категорийные).** `package/library/skills/<category>/` — только с сохранением исходных лицензионных заголовков файлов.
6. **Tools.** `tools/*.ps1` — только ASCII (см. «Кодировки»); Python — stdlib-only, запуск `python -X utf8`.

## Запреты (PR будет отклонён)

- генерация значений флагов (всегда) и попадание значений в публичный репозиторий: перед PR вычищай/маскируй (`<префикс формата>{...}`); механика проверки и формат из условия — можно;
- названия соревнований/организаций/ников, любые попытки деанона;
- личные пути (`C:\Users\<имя>\`, `/home/<имя>/`), секреты, PII;
- дампы > ~200 строк — выноси суть, команды, выводы;
- удаление/переписывание чужих записей (только дополнение с пометкой `[update: YYYY-MM-DD]`);
- переименование каталогов скиллов (платформы привязаны к именам).

## Процесс PR

1. Ветка: `lesson/<date-slug>` для знаний, `feat/<topic>` для остального.
2. Самопроверка локально: `tools/check_package.ps1` → `RESULT: 0 (clean)`.
3. PR: 1–2 предложения — что добавлено и почему это важно; категория (knowledge/skill/tool/eval).
4. CI (`checks`) должен быть зелёным: гигиена пакета (запрещённые сущности).
5. Один approve → merge. Для lesson-записей merge без squash (история знаний важна).

## Версии

`package/VERSION` и `package/CHANGELOG.md` обновляет мейнтейнер при изменениях структуры/скиллов/промпта. Отдельные lesson-записи bump версии не требуют.

## Кодировки и платформы

- Markdown: UTF-8; пути внутри пакета — только относительные.
- `.ps1`: **только ASCII** — Windows PowerShell 5.1 читает файлы без BOM как ANSI, кириллица в коде/строках ломает парсер (проверено на практике).
- Скрипты eval запускать как `python -X utf8 ...` (корректный вывод в Windows-консолях).

## Вопросы и идеи

Сначала Issue с описанием, потом код. Большие изменения (новый скилл, смена структуры) — обсудить в Issue до реализации.
