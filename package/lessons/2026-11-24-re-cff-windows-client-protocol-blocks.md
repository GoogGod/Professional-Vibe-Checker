# Сетевая CFF (REV medium) — протокол исполняемых блоков

Разбор Windows-бинарника, который общается с сервером по кастомному протоколу:
все кадры `[u32 len][тело]`. Библиотека/инструменты: capstone, python3, прокси-логгер.

## Протокол

- Клиент -> сервер:
  - hello: `[len=4][00 00 00 00]`
  - решение: `[len=20][u32 var=1][u64 block_id][u64 label]`
  - host-call fetch: `[len=12][u32 var=2][u64 id]`
- Сервер -> клиент:
  - BlockImage: `[u8 01][u64 id][u64 ilen][code][u8 cache]` (формат с маркером 0x01; не путать с обычным var=0/1)
  - ответ на решение: `[u32 var=1][u64 next_block][u64 len][code][u8 cache][u64 pending]`
  - reject: `[u32 var=3]` (wrong) и `[u32 var=4]` (reject)
  - host-call запрос: `[len=4][u32 var=2]`

## Ключевые наблюдения

1. Клиент исполняет серверные блоки нативно (VirtualAlloc RWX + FlushInstructionCache + call rdi); блоки читают/пишут контекст фрейм-стека (`rcx` = указатель на контекст).
2. Блоки — это машинный код x86-64: чаще всего заканчиваются `movabs rax, <label>; ret`. Сервер решает, какой блок слать следующим, по вернувшейся метке.
3. Ответы сервера приходят партиями; есть фаза «чтение строки»: блоки вызывают `GetStdHandle(-11)` и `ReadFile` через host-call (таблица функций в контексте по смещениям +0x90/+0x98/+0xa0).
4. Строка ввода проверяется в **первой фазе** (до приглашения `input: `): блоки вида `mov rax,[rcx+0xc8]; cmp byte ptr [rax+off], val; cmov* rax, rcx; ret`. Важно: **подача строки сразу после старта** (не дожидаясь `input: `) меняет поведение — диалог расширяется и не падает в wrong мгновенно.
5. Проверка длины: блок `cmp qword ptr [rcx+0x30], 0xc8` (200); полярность cmov/cmovne разная у разных блоков — нельзя предполагать, что всегда нужна одна и та же ветка.
6. Оракул: подмена метки пары на альтернативную (`L_true` вместо `L_false`) вызывает REJECT — сервер строго сверяет ожидаемую метку.
7. Обойдное «кольцо accepted»: блоки 0x580c -> ... -> 0x2b46 -> 0x14290 ведут к печати accepted, но это не даёт флаг: сервер просто продолжает слать блоки (петля 0x88f7/0x3952). Флаг из этого пути не извлекается.

## Инструменты, созданные в ходе решения

- `fetch_block.py` — вытаскивает блоки по id с сервера (host-call fetch) и сохраняет .bin.
- `parse_all_s2c.py` + capstone — дизассемблирование тел блоков из лога прокси, поиск cmp/cmov.
- `full_pass.py` / `feed_early.py` / `len_scan.py` — passthrough-прокси с полным логированием S2C/C2S и управляемой подачей stdin (ранней или по приглашению).
- `ring_walk.py` — автоматический проход по графу блоков с вычислением меток из кода. 

## Итог

Флаг не получен. Главные гипотезы, оставшиеся неразрешёнными:
- правильная строка = 200 байт, удовлетворяющих всем cmp-проверкам первой фазы (с учётом индивидуальной полярности cmov);
- ранняя подача строки (до `input: `) — обязательна, иначе строка не попадает в проверяемый буфер;
- вероятно, после успешного прохождения первой фазы сервер продолжит диалог и выдаст блок, содержащий флаг (или клиент его напечатает).
