# PyInstaller-реверс «проклятого» байткода: скрэмблинг опкодов, блэкбокс-калибровка, инъекция сидкара

- **Дата:** 2026-10-23 (полевой solve, hard; 2 ч 08 м, с одной подсказкой оператора — префикс флага)
- **Категория:** reverse / Python / PyInstaller
- **Ключевые слова:** PyInstaller, CArchive, code object, скрэмблинг опкодов, калибровка опкодов, PYZ, fnv1a32, sidecar

## Стек задачи

PyInstaller onefile ELF, Python 3.13, code object `__main__` искажён: имя без `.pyc`, disassembly падает (co_code ссылается на индексы вне диапазона).

## Инструменты, которых не оказалось (и что писать самому)

- `pyinstxtractor` — нет в Kali; в Python ≥3.11 менялся парсер marshaled-объектов, а полевые форки не знают Python 3.13.
- `xdis`/`decompyle3`/`uncompyle6` — не поддерживают 3.13.
- Свой экстрактор CArchive: COOKIE magic `MEI\x0c\x0b\x0a\x0b\x0e`, OS-флаги (3=linux, 0/1=win), lengthofPackage, tocOffset, tocLen; TOC-записи парсить `pos+c overlaid` (entry struct: entrySize/1B + pos/4B + cmprsdDataSize/4B + uncmprsdDataSize/4B + cmprsFlag/1B + typeCmprsData/1B + name/…). **Грабли**: в старом cookie `pyver` читается как `313` — это 3×100+13, а не версия файла.
- Толерантный дизассемблер: читать code object байт-за-байтом, ловить out-of-range и co_exceptiontable как обычный байтовый blob.

## Три «проклятия» и вскрытие

1. **Скрэмблинг опкодов**: байткоды Python ≥3.11 имеют операнды CACHE (по 1 на большинство опкодов) и валидный адаптивный интерпретатор, НО table-порядок опкодов у каждой минорной версии свой. Сломанный co_code = опкоды переставлены → dis отрабатывает, но семантика мусорная.
2. **Калибровка таблицы опкодов по блэкбоксу** (главный приём): интерпретатор самой цели остаётся эталоном — подаём микро-программы (только `LOAD_CONST`/`RETURN_VALUE` и один тестируемый опкод) в sidecar-режиме, смотрим output/исключения → по реакции однозначно восстанавливаем значение опкода (7×, >,<, ==, if/else, BINARY_SUBSCR…). Никаких догадок — только измерения.
3. **PYZ-архив внутри**: zlib per-entry + TOC-записи (typePos/1B + osPos/4B + length/4B + uncompressed/4B + flag/1B + type/1B + name). Внутри `encodings.ascii`, `codecs` и пр. — сравнение их КОРОТКИХ функций с эталонными (из локального Python) даёт якоря для той же таблицы опкодов (одна и та же логика → одинаковые структуры).

## Sidecar-инъекция (когда декомпиляция бессильна)

PyInstaller bootloader ищет `pyi-windowed`/аргументы; собственный ELF-мод: пересобрать валидный PyInstaller-архив с нашим code object как `__main__` (без onefile-компрессии) → прогоняем МИКРО-программы прямо в интерпретаторе цели. Это быстрее, чем подбирать опкоды по exe-диффам.

## Финал: constrain-solving вместо реверса логики

Найден массив `expected_hashes` (144 sha256-подобных хэшей; фактически fnv1a32), `transform(ch)` из переключателя — каждый символ флага независимо хэшируется и сверяется с массивом. Порядок не важен (параллельный solver по каждой позиции 0..35, перебор алфавита), одна позиция осталась амбигентной (2 кандидата) → оператор дал префикс → финальная строка сошлась, проверена оригинальным бинарником («You got it!»).

**Урок**: если логика сводится к per-symbol хэш-сверкам — не реверсить поток управления, а решать систему ограничений; last-mile (амбигентная позиция) — вопрос оператору, а не ещё час перебора.

## Грабли окружения

- `python3 -m pip install pyelftools` на цельевой машине не нужен — достаточно struct.
- WSLENV/переменные не переносятся автоматически — пайпы unix-утилит только внутри `bash -c`.
- Если sha256-хэши коротких инпутов не сходятся с локальными — это fnv1a32 (или другой 32-бит хэш), проверять до попыток «сломанного sha256».

## Переносимое (в один абзац)

PyInstaller-цель на нестандартном Python — это два реверса: формат-упаковка (CArchive/PYZ — пишем свой парсер за ~200 строк) и сам интерпретатор (таблица опкодов — калибруем блэкбокс-микропрограммами, эталон внутри цели). Декомпилятор не нужен: sidecar-инъекция + решатель ограничений закрывают 90% таких задач быстрее, чем портирование дизассемблера.
