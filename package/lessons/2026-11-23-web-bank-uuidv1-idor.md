# 2026-11-23 Web: «Винтажный банк» (easy) — IDOR через предсказуемый UUIDv1

## Суть
- Визуальная новелла «банк» на Python (VaultQuest/1.0): три API:
  `POST /api/rent` (выдаёт `{token, cell}`), `GET /api/cell/<token>`
  (возвращает `{cell, owner, flag}`), `GET /api/ledger` (книга вкладов:
  26 вкладчиков: имя, дата открытия вклада до секунды, номер ячейки).
- Токены — **UUIDv1**: `time`-часть = системное время аренды,
  `clock_seq=0x9a2b`, `node=0x0242ac110002` фиксированы (проверено:
  uuid из ответа rent переводится в unix-время ровно совпадающее с
  Date-заголовком ответа).
- Ledger отдаёт точное время открытия каждого вклада -> UUID известного
  вкладчика восстанавливается однозначно: `uuid1_at(datetime_strptime(date))`.

## Шаги
1. `GET /api/ledger` — забрать список вкладчиков (имя/дата/ячейка).
2. Составить UUIDv1 для каждой даты:
   ```python
   greg = datetime.datetime(1582,10,15)
   ts = int((dt - greg).total_seconds() * 1e7)
   uuid.UUID(fields=(ts & 0xffffffff, (ts>>32)&0xffff,
                     ((ts>>48)&0x0fff)|0x1000, 0x9a, 0x2b, 0x0242ac110002))
   ```
3. `GET /api/cell/<uuid>` — открывать восстановленные ячейки, пока
   `flag` не станет непустым.

## Признаки / ловушки
- Сервер не проверяет «право собственности» на токен: любой валидный
  UUID (т.е. существующая запись) отдаёт содержимое ячейки.
- Несуществующий UUID -> `{"cell":null,"owner":null,"flag":null}` — это
  не ошибка, а отсутствие записи; по нему легко отличить «пусто» от
  «нет такой записи».
- `cell` в ответе rent вычисляется из UUID (первые 6 hex символов %
  30 + 1), но в БД хранится отдельно; попытка слать номер ячейки
  вместо UUID не работает.
- API минимален: других эндпоинтов нет (openapi/docs отсутствуют),
  SQLi/path-traversal не проходит; единственный вектор — предсказуемость
  UUIDv1.
- Флаг лежал в ячейке одного из вкладчиков (Уточкин, cell 6).

## Итог
- [FLAG] получен. Восстановление UUIDv1 по известному времени создания
  записи + отсутствие проверки владельца = IDOR.
