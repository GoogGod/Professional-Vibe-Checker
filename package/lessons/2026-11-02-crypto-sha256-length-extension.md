# Length extension: подпись sha256(secret || msg)

Суть: сервис проверяет подпись `sig = sha256(secret || msg)`. Имея одну валидную
пару (msg1, sig1) из логов/трафика, можно дописать к msg1 SHA-256 padding + новый
блок и вычислить валидную подпись без знания secret.

## Шаги
1. Выяснить длину secret:
   - `secret = sha256(password).hexdigest().encode()` → **64 байта** ASCII-hex;
   - digest-вариант (32) обычно не подходит → «incorrect signature» в логах.
2. Формула:
   - `pad = b'\x80' + b'\x00' * ((56 - (secret_len + len(msg1) + 1) % 64) % 64) + (secret_len + len(msg1)) * 8 → 8 байт big-endian`
   - `msg2 = msg1 + pad + append`
   - `sig2 = extend_hash(sig1, len(msg1), append, secret_len=64)` — продолжение SHA-256 с известного состояния.
3. Отправить msg2 + sig2; проверить эффект через state/логи.

## Детали
- Сервер применяет одно действие за сообщение (последнюю пару action/duck) —
  для нескольких жертв отправляй отдельные сообщения.
- Действия применяются из очереди раз в ~5 сек — ставь критичные первыми.
- При `running=no` запросы игнорируются — сначала запусти процесс/гонку.
- После бинарного LE с того же аккаунта последующие обычные действия могут
  игнорироваться — отправляй LE последним или используй отдельный аккаунт.
- Обычные действия от своего имени могут молча игнорироваться, если права только
  у другого user — используй LE от того user.

## Типичные грабли
- Длина секрета (32 vs 64) — самая частая причина «incorrect signature».
- Не ставить обычные действия перед LE: очередь раз в ~5 сек, LE должен успеть
  до завершения раунда (гонка идёт 25–40 сек).
- Не смешивать LE и обычные prep в одной очереди с одного аккаунта.
