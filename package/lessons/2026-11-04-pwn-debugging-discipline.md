# PWN: дисциплина отладки — как НЕ растрачивать время (разбор сессии)

Ретроспектива реальной сессии (задача «музей», tcache/hook). Опыт
показывает, где агент «спотыкался» и что исправить.

## Типичные ошибки
1. **Версионный хаос**: ~20 скриптов (`t2.py`, `mini3.py`, `diag.py`,
   `hexflow.py`, `loc_discard.py`, …) вместо эволюции ОДНОГО файла.
   Каждая малая вариация — новый файл → теряется преемственность,
   смутно видны изменения.
2. **Слепые sleep вместо чтения промптов**: `time.sleep(0.5)` и отправка
   команд без `recv_until(": ")` — протокол рассинхронизируется,
   «Unknown option», отладка вслепую.
3. **Диагностика через hex-дамп всего подряд** (`hexflow.py`): не было
   модели вывода; вместо этого лучше было интерактивно поиграть меню и
   выяснить формат каждого ответа один раз.
4. **Смена цели с шелла на команды МЕДЛЕННО**: получив `/bin/sh`,
   долго пытались заставить его работать интерактивно; быстрее —
   сразу перейти на `system("cmd")` по одному запуску.
5. **Нет раннего локального прогона**: часть попыток шла на remote
   вслепую; локальный бинарник с теми же шагами (remove→system) даёт
   точную картину вывода.

## Рекомендации (чек-лист перед эксплойтом)
1. Один файл-скелет: класс соединения + примитивы меню (add/edit/
   inspect/remove) + `recv_until` + `recv_all(timeout)`.
2. Сначала «ручной» проход меню (несколько add/edit/inspect), записать
   формат каждого ответа в комментарии.
3. Локально прогнать каждый шаг (leak, hook, trigger) ДО remote.
4. Readback'и: после каждой записи читать/проверять, что записалось.
5. Для команд: маркерные строки (`MARK_START/END`) в выводе, а не
   тайминги.
6. Только после стабильной локальной работы — запускать на remote,
   передавая CMD параметром (не константой).
