# Урок: первый Attack/Defense — как иметь first blood и слить день (полевой разбор 7 часов)

Дата: 2026-10-25 · Категории: attack/defense, process, ops · Уровень: tournament · Исход: середина таблицы при пике в топ-3 к середине дня; потери кратно превысили кражи

Один день, сотни раундов, несколько сервисов, режим сгорания флагов на лежащем сервисе. Всё, что ниже — проверено кровью, каждая ошибка стоила очков. Урок длинный намеренно: это конвейер решений, а не список фактов.

## 0. Хронология дня (чтобы видеть динамику)

- **T−0…T+42 мин: инфраструктурный ад.** Подключение (VPN + SSH) съело 42 минуты из 60 подготовительных. При этом к T+40 всё уже было починено.
- **T+0…T+60 (первый час после открытия сети): триумф.** Рабочая ферма сада флагов, first blood по простому сервису, 3-е место.
- **Остаток дня: медленное утекание.** Свои сервисы падают от собственных патчей и перегруза → режим сгорания сжигает добытое → некогда патчить нормально → чужие доят нашу главную дыру → итог — середина таблицы.

Вывод №0: **A/D выигрывается стабильностью, а не взломом.** Мы вскрыли 2 сервиса из 4 быстрее многих и всё равно проиграли днём — потому что защита и стабильность кормят атаку (см. §3).

## 1. Preflight решает полдня (чего не сделали — и что обязательно делать)

Провал: 42 минуты на подключение. Причины по убыванию цены:

1. **`sshpass` не был установлен** заранее. Час дебага самодельных pty-скриптов для ввода пароля в ssh. Правильная связка на всё game-day:
   ```bash
   PW=$(tr -d '\r\n' < vulnbox.txt)          # CRLF срезать ВСЕГДА
   sshpass -p "$PW" ssh-copy-id -i ~/.ssh/id_ed25519.pub root@<vulnbox_ip>
   # дальше только ssh -i, паролей нет вообще
   ```
2. **Фоновые процессы убиваются платформой** (~10-минутный таймаут фоновых задач). VPN поднимался, умирал, «пингов нет / порт 22 closed» — а причина была в мёртвом туннеле, не в сети. Лечение (найдено опытно): `setsid nohup ... &` — демон переживает задачу. **Репетировать это до турнира.**
3. **Путаница игроков**: конфигов в архиве много (player001…007), оператор в панике менял решение («мы player001» → «пофиг, бери последнего»). Фиксировать конфиг заранее и не трогать.

Чек-лист за день до старта (все пункты — руками, один раз):
- [ ] `age`, `openconnect`, `sshpass`, `nmap` стоят в атакующей ОС;
- [ ] ключ `~/.ssh/id_ed25519` сгенерирован;
- [ ] репетиция: поднять VPN демоном (`setsid nohup`), проверить `curl scoreboard`, убить, поднять снова;
- [ ] скрипт `vpn_start.sh` + `start_farm.sh` написаны и протестированы;
- [ ] известно, ЧТО убивает фоновые процессы, и как делать выживающих демонов.

## 2. Что сработало блестяще (не потерять)

- **Молотилка с первого раунда.** `farm.py` (~150 строк stdlib: config → teams → attack_data → exploits/* → очередь → батч PUT) была поднята ДО открытия сети и дала first blood на 3-й минуте: 4 флага, ~70 очков за один. Эксплойт-контракт `exploit(host, port, hints) -> [flags]` + автозагрузка из каталога — новый эксплойт от субагента подхватывался рестартом фермы без правки ядра.
- **Реальные имена сервисов — из API** (`/api/client/tasks/`), а не из брифинга: в брифе были имена из примера, в жизни оказались другими. Ничего из брифинга не принимать на веру, всё сверять с `/api/client/config/` и `/api/client/tasks/`.
- **Субагенты по сервисам** — идеальное применение spawn_task: задача на сервис, воркопы копают исходники (нашли 7 семейств векторов в одном Rust-сервисе), готовые эксплойты складывают в каталог фермы. Главный чат не тратил контекст на чтение кода — 3 переполнения контекста всё равно случились, без субагентов было бы 10.
- **watch.py** (scoreboard каждые 30 с, алерт при не-OK) — ловил падения раньше оператора.
- **Отключение эксплойта-балласта** спасло живые линии (см. §5).

## 3. Петля сгорания — главный механизм дня (понять и вбить себе в рефлексы)

Режим сгорания: флаги, добытые на сервисе X, засчитываются, только если **твой собственный** сервис X в статусе OK. Дальше цепочка:

```
мой сервис X DOWN/MUMBLE
  → чекер не может класть/читать флаги на моём X
  → у меня нет hints по X в attack_data (не знаю, ГДЕ у чужих флаг)
  → мой эксплойт X нечем питаться → 0 флагов с X
  → + сгорают уже добытые X-флаги
```

Наблюдение дня: «ни одного флага по двум сервисам за десятки раундов» — обе строчки объяснялись не слабым эксплойтом, а **лежащими своими инстансами этих же сервисов**. Эксплойт был готов и рабочий. При подъёме сервиса hints появлялись через 1–2 раунда — и флаги шли.

Правила, которые из этого следуют:
1. **Статус своих сервисов важнее любого эксплойта.** Порядок приоритетов: SLA → свои эксплойты-кормушки → новые векторы.
2. Чекер — тоже клиент: **любой патч, ограничивающий поведение, сначала прогнать на чекер-сценарии** (положить/прочитать как чекер руками), и только потом в прод.
3. Откат — первая реакция на не-OK после твоего патча. Откатил → статус вернулся → разбираешь не спеша. «Починить на живую» дороже.
4. Диагностика падения — по `/public/scoreboard/teamtasks/<team>/<task>/logs` (у нас было — читали причины CHECK FAILED по шагам чекера).

## 4. NAT-реальность: все приходят с одного IP

Весь входящий игровой трафик (и чекеры, и атакующие команды) приходил на vulnbox **с одного NAT-адреса платформы** (вида 10.x.x.1). Следствия:

- **Бан/лимит по IP — запрещён**: забанишь чекера вместе с атакующим (получишь CORRUPT/DOWN).
- «Trusted IP» логика в патче — мёртвый груз: различий по IP просто нет.
- Отличать чекера можно только по поведению (полнота сценария, паттерны запросов, время) — и лучше вообще **не отличать**, а закрывать уязвимость как класс, не трогая легитимные операции.

## 5. Эксплойт-балласт и гигиена фермы

- **Мёртвый эксплойт хуже отсутствия**: линия по одному сервису держала 40 UUID-целей × 30 с таймаута каждый цикл — 0 флагов (математика вектора была безнадёжна: гонка за первую строку, которую чекер всегда занимает первым). Пока она молотила — флаги другого сервиса **старели в очереди** («Flag is too old»). Отключение мёртвой линии мгновенно оживило живую.
  Правило: эксплойт с метрикой «N циклов → 0 флагов → тратит слоты пула» отключается без сожалений. Ферма — стадо доильных коров, а не музей.
- **Seen-файл обязан персиститься на диск** (рестарт фермы терял дедуп → «already stolen» → напрасные сабмиты → риск slow-mode).
- **Свои флаги не сабмитить** (фильтр по своему IP) — мусорные сабмиты тоже двигают к slow-mode.
- «Flag already stolen» на рабочей линии = конкуренты быстрее; ответ — скорость цикла (раунд 60 с; кража → сабмит должен укладываться в 1–2 раунда), а не новые попытки того же.

## 6. Дренаж: своя кормушка должна быть закрыта В ТОТ ЖЕ ЧАС

Самая дорогая ошибка дня. Мы сами доили простой сервис (успешно, в больших количествах), но **у себя его же дыру не закрыли** — счётчик краж у нас перевалил за сотни (итог: потери кратно больше краж). Дилемма «патчить (риск сломать чекера) vs оригинал (дыра открыта)» реальна, но решается не выбором одного:
1. Закрыть дыру **у себя немедленно**, даже грубо (это не ломает чужих — exploitable у них остаётся).
2. Грубый патч может сломать чекера → поэтому патч = «убрать вектор, не трогая легитимный путь», + чекер-тест, + снапшот для отката.
3. Если патчить страшно — «канализировать» дыру (например, рандомизировать/шифровать место хранения флага), а не закрывать endpoint.

Симметричное правило: **каждая найденная у себя уязвимость = одновременно готовый эксплойт против всех**. Один анализ кормит обе стороны — и обе стороны надо закрывать/использовать с одинаковой скоростью.

## 7. Мелочи, стоившие очков (коротко)

- `pids-limit`/`prlimit` для контейнера **теряются при пересоздании** (docker compose up) — сервис потом падает с паниками. Ресурсные лимиты фиксировать в compose-файле, а не в рантайме.
- Лабораторные контейнеры («разведём копию сервиса на боевом боксе») подняли load average до 17 → таймауты чекера → MUMBLE. Лаборатории — на свою машину, не на vulnbox.
- Бэкап (289 МБ по scp) тянулся во время открытия сети. Бэкапить в первый час только исходники/конфиги (десятки МБ), не образы.
- Первый бэкап должен быть **до первого патча** — мы почти успели, но на грани.
- 3 переполнения контекста главного чата: состояние (STATE.md) перечитывалось с диска — это спасало; но сам чат забивался логами проверок. Держать главный чат чистым: всё тяжёлое — субагентам и скриптам, в чат — только сводки.

## 8. Мораль

1. **Стабильность > взлом.** Проиграли не потому, что не вскрыли сервисы (вскрыли быстро), а потому что свои падали, а дыра дня не была закрыта у себя.
2. **Режим сгорания превращает защиту в топливо атаки** — см. петлю §3 и рефлекс «свой сервис OK — иначе всё сгорает».
3. **Preflight за день до старта окупается first blood'ом.**
4. Скорость кражи → сабмита (1–2 раунда) — материальна; медленная ферма = «already stolen».
5. Система (BOOT-П1–П6 + скилл + бриф + субагенты) в целом выдержала день: 66 М входных токенов, 325 Bash, 8 субагент-задач, и при этом first blood и рабочий пайплайн с первой минуты. Проигрыш — тактический, не системный. Устранимый.
