# Length extension: подпись sha256(secret || msg)

## Признаки
- Форма/API: `sig_hex_prep` + `msg_hex_prep` (или sig + msg в hex).
- Правила/подсказка: `sig = sha256(secret || message)`, `secret = sha256(password)`.
- В логах `/logs` видны пары msg + sig со статусом ok/incorrect signature.
- Права на действия различаются по полю `user` внутри msg (например, привилегированное действие доступно только `user:<admin>`).

## Шаги
1. Определи схему секрета:
   - `secret = sha256(password).hexdigest().encode()` → **64 байта** ASCII-hex (проверено).
   - digest-вариант (32 байта) обычно НЕ подходит.
2. Найди валидную пару (msg1, sig1) от нужного user в логах/трафике (статус ok).
3. Вычисли length extension:
   - `secret_len = 64`
   - `pad = b'\x80' + b'\x00' * ((56 - (secret_len + len(msg1) + 1) % 64) % 64) + (secret_len + len(msg1)) * 8 → 8 байт big-endian`
   - `msg2 = msg1 + pad + append` (append — новое действие, например `&action:<action>&duck:<duck>`)
   - `sig2 = extend_hash(sig1, len(msg1), append, secret_len=64)` — продолжить SHA-256 со внутреннего состояния, зная digest.
4. Отправь msg2 + sig2. Проверь эффект через state/логи.

## Важные детали
- Сервер применяет ОДНО действие за сообщение (последнюю пару action/duck) — для нескольких жертв отправляй отдельные сообщения.
- Действия применяются из очереди раз в ~5 секунд — ставь критичные первыми.
- При running=no запросы игнорируются — сначала запусти гонку/процесс.
- После отправки бинарного LE с того же аккаунта последующие обычные действия могут игнорироваться — либо отправляй LE последним, либо используй отдельный аккаунт.
- Обычные действия от своего имени (привилегированное действие) могут молча игнорироваться, если права только у другого user — используй LE от того user.

## Проверенная имплементация
- extend_hash / sha256_pad: типовой код продолжения внутреннего состояния SHA-256 (блоки 64 байта, K-константы, ROTR).
- Пример успеха: дисквалификация защищённой сущности через LE от admin-пользователя (2026-11-01).
