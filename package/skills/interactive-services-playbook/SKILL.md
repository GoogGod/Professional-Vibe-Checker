# Интерактивные сервисы — тактика и кейсы

Скилл для задач, где нужно **взаимодействовать с сервисом** (сокет/TCP, игровой бот, криптопротокол). Обобщённый опыт архивных серий; не привязан к конкретному соревнованию. Флаги не хранятся.

## 1. Общий подход

- Сначала **изучи протокол**: как устанавливается соединение, формат сообщений (JSON/бинарные фреймы), кто первый говорит, что считается завершением раунда.
- Сохраняй **все ответы сервера** в лог-файл — по ним восстанавливается поведение и правила.
- Пиши клиент на Python (sockets/pwntools); добавляй устойчивость: таймауты, ретраи на дисконнекты, идемпотентность шагов.
- Тестируй логику локально на копии (если сервер/логика выданы) до отправки на боевой сервис.
- Фиксируй состояние между попытками (лог партий/транскриптов), чтобы анализ переживал перезапуск.

## 2. Игровые боты (сокет-игры)

- **Кейс: настольная игра (например, backgammon-подобная)**. Известный паттерн: клиент-бот играет против сервера-бота; нужна серия побед (например, 10 побед с ограниченным числом попыток).
  - Внутри артефактов могут быть **файлы весов** (например, ~122 float: contact/race) — сохрани копии: возможно, они и есть ключевой артефакт этапа.
  - Оценка позиции: веса + pip-разности; выбор хода = максимум оценки. Классический подход в стиле pubeval.
  - Тестируй правила клиента: бар, снятие фишек, корректность пипсов — грубые ошибки клиента проигрывают игру.
  - **Адаптивный оппонент**: не повторяй один и тот же паттерн; анализируй лог партий, ищи, на чём сервер ловит.
  - Учитывай тайминги (лимит на ход); при отклонениях сервером — разбирай протокол-фреймы.
- Общее для игр: изучи, где хранится счёт и как определяется победа; проверь, нет ли способа честно завершить игру быстрее (например, корректный форс-ход при доказанном преимуществе).

## 3. Крипто-протоколы (commit → challenge → response)

- **Кейс: интерактивный крипто-сервер** (обмен JSON-строками; sample-транскрипт в комплекте).
  - Алгебра может быть «декоративной» (гиперэллиптические поверхности, якобианы) — сначала сверь **реализацию** проверки с математикой: злоупотребление тождествами часто даёт подделку commitment/response.
  - Ищи утечку nonce, переиспользование точек, малые подгруппы, отсутствие проверки подгруппы.
  - Сравнивай sample-транскрипт с реализацией: расхождения = вектор.
- **Кейс: точки на кривой + conic** («полярные» преобразования): восстанови соотношения между точками (скалярные связи), проверь составной модуль, аномалии, малые подгруппы; название задачи часто намекает на преобразование («подъём/спуск» между кривыми).
- Инструменты: sympy/sage-подходы; малые discrete log — BSGS/Pollard.

## 4. Сетевые заготовки

- rwntools/pwntools: `remote(host, port)`, recvuntil(), JSON-обмен; логируй все строки.
- Для фаззинга протокола — minimizer входа (бисекция сообщений); для replay — сохраняй полные транскрипты.
- Защита от дисконнектов: reconnect-обёртка; состояние клиента — в файл, чтобы продолжать без потери прогресса.
- Не забывай про байтовые кодировки (UTF-8, \r\n vs \n, длина фрейма).

## 5. Анти-паттерны

- Не «допиши сервер под себя» — правило сервера неизменно; подстраивай клиента по логам.
- Не сдавай кандидатный «флаг» из трассировки, пока он не полный и не подтверждён форматом задачи (в логах бывают усечённые фрагменты).
- Не полагайся на память: веди журнал попыток и результатов в `STATE.md`.

## Готча (ловушки)
- Ставь таймаут на сокет (`settimeout(3)`) — зависшее ожидание съедает раунды.
- Фиксируй формат ответов (base64/hex/JSON) до парсинга.
- Не слай всё одним send: многие сервисы буферизуют по строкам.
- Бот с паузой между ходами: измерь тайминги и держи очередь ходов, не торопись.
